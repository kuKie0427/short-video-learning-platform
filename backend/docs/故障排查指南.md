# 故障排查指南

本文按"症状 → 根因 → 解决"组织。每条先给出可观察的症状，再定位到代码或配置中的根因，最后给出修复动作。文中所有命令、路径、端口、配置键均与当前代码一致。

## 一、快速定位

先跑一键诊断脚本，它会检查容器状态、基础设施健康、各服务健康检查与最近错误日志：

```bash
cd backend
./scripts/diagnose.sh
```

等价的手工命令：

```bash
# 容器状态
docker-compose ps

# 基础设施
docker-compose exec -T postgres pg_isready -U app_user
docker-compose exec -T redis redis-cli ping
docker-compose exec -T kafka kafka-broker-api-versions --bootstrap-server localhost:9092

# 服务健康检查
curl -s http://localhost:8001/health
curl -s http://localhost:8002/health

# 最近错误
docker-compose logs --tail=100 | grep -i error
```

## 二、症状与根因

### 症状1：`docker-compose ps` 显示服务不是 Up

服务容器未启动或反复重启。

**根因A：容器启动失败**

查看日志定位具体异常：

```bash
docker-compose logs auth-service
docker-compose logs content-service
```

常见异常与对应根因：

| 日志异常 | 根因 |
| --- | --- |
| `ModuleNotFoundError: No module named 'common'` | 镜像未包含 common 目录或 PYTHONPATH 未设置，见症状4 |
| `sqlalchemy.exc.OperationalError: could not connect to server` | 数据库连接失败，见症状2 |
| `redis.exceptions.ConnectionError` | 生产环境 Redis 连接失败，见症状3 |
| `OSError: [Errno 98] Address already in use` | 端口被占用，见症状6 |

**根因B：代码错误**

```bash
docker-compose logs -f auth-service | grep -i error

# 本地检查语法
cd services/auth
python -m py_compile app/main.py
```

### 症状2：数据库连接失败

日志出现 `sqlalchemy.exc.OperationalError: could not connect to server`，或接口返回"数据库操作失败"。

**根因A：PostgreSQL 未启动**

```bash
docker ps | grep postgres
docker-compose up -d postgres
docker-compose logs postgres | grep "database system is ready"
```

**根因B：连接字符串错误**

`common/config/settings.py` 优先读取环境变量 `DATABASE_URL`；未设置时用 `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` 拼出 `postgresql+psycopg://` 连接串。docker-compose.yml 中 auth-service 的期望值：

```bash
docker-compose exec auth-service env | grep DATABASE
# DATABASE_URL=postgresql://app_user:app_password_2025@postgres:5432/short_video_platform
```

**根因C：数据库未初始化（表缺失）**

服务启动时 `common/database/connection.py` 的 `init_db()` 会执行 `Base.metadata.create_all` 自动建表；表结构变更由 alembic 迁移管理。若表缺失或结构过期，在宿主机执行迁移（compose 已将 5432 映射到宿主机）：

```bash
cd backend
DATABASE_URL=postgresql://app_user:app_password_2025@localhost:5432/short_video_platform alembic upgrade head
```

### 症状3：Redis 连接失败

`common/database/connection.py` 的 `get_redis()` 在连接失败时按环境区分行为：

- 开发环境（`ENVIRONMENT=development`）：返回 None，服务继续启动，日志出现 `Redis连接失败（将使用内存存储）`。短信验证码降级为内存存储，推荐缓存与播放统计失效。
- 生产环境（`ENVIRONMENT=production`）：抛出 `redis.exceptions.ConnectionError`，服务启动失败。

**根因A：Redis 未启动**

```bash
docker ps | grep redis
docker-compose up -d redis
docker exec -it short_video_redis redis-cli ping   # 应返回 PONG
```

**根因B：连接配置错误**

`get_redis()` 优先使用 `REDIS_URL`，否则用 `REDIS_HOST/REDIS_PORT/REDIS_DB/REDIS_PASSWORD`。检查容器内实际值：

```bash
docker-compose exec auth-service env | grep REDIS
```

### 症状4：`ModuleNotFoundError: No module named 'common'`

服务代码通过 `from common.config.settings import settings` 等语句导入共享库，Python 必须在 `sys.path` 中找到 backend 根目录。

**根因A：本地运行时工作目录不对**

所有服务的 `app/main.py` 启动时都会把项目根目录加入 `sys.path`：

```python
project_root = os.path.abspath(os.path.join(os.path.dirname(__file__), '../../..'))
sys.path.append(project_root)
```

本地运行需在服务目录下启动（如 `cd services/auth && uvicorn app.main:app`），或设置 `PYTHONPATH` 指向 backend 根目录。

**根因B：镜像未包含 common 目录**

所有服务的 Dockerfile 都先复制 common 再复制服务代码，并设置 `ENV PYTHONPATH=/app`：

```dockerfile
COPY common/ ./common/
COPY services/auth/ ./services/auth/
ENV PYTHONPATH=/app
```

若镜像构建于目录结构调整之前，重建镜像：

```bash
docker-compose build auth-service
docker-compose up -d auth-service
```

**根因C：common 目录结构被改动**

共享库目录为 `backend/common/`，包含 `models/`、`config/`、`database/`、`utils/`、`messaging/`。检查：

```bash
ls -la backend/common/
ls -la backend/common/models/
ls -la backend/common/config/
ls -la backend/common/database/
ls -la backend/common/utils/
```

### 症状5：`ImportError: cannot import name 'xxx' from '...'`

**根因**：API 文件缺失、被重命名，或导入路径与文件实际位置不一致。每个服务的 `app/api/` 下都有对应路由文件，且都定义了 `router` 变量（如 `services/auth/app/api/auth.py` 中的 `router = APIRouter(prefix="/api/auth", ...)`）。

```bash
ls -la services/auth/app/api/auth.py
cat services/auth/app/api/auth.py | head -20
ls -la services/auth/app/api/__init__.py
```

### 症状6：端口冲突

启动日志出现 `OSError: [Errno 98] Address already in use`，或 `curl` 访问到的是另一个程序。

**根因**：宿主机端口被占用。服务端口映射见 docker-compose.yml：auth 8001、content 8002、upload 8003、split 8004、course 8005、search 8006、notification 8007。

```bash
lsof -i :8001
lsof -i :8002
```

**解决**：

```bash
# 停止占用端口的进程
kill -9 <PID>

# 或修改 docker-compose.yml 的端口映射，例如 "8001:8001" 改为 "18001:8001"
```

### 症状7：服务启动后立即退出

**根因**：启动阶段抛异常。服务启动时依次执行 `init_db()`（建表）、Redis 连接测试；auth-service 额外执行 `validate_startup_config()` 配置校验（生产环境校验 `JWT_SECRET_KEY` 与 `CORS_ORIGINS`）。任一环节抛异常都会导致进程退出。

```bash
docker-compose ps                    # 查看退出码
docker-compose logs auth-service     # 查看完整日志
```

常见根因：数据库连接失败（症状2）、生产环境配置校验失败（`JWT_SECRET_KEY` 未设置或为默认值、`CORS_ORIGINS=*`）、导入错误（症状4/5）。

### 症状8：服务因依赖未就绪而不启动

`docker-compose ps` 中服务停留在未启动状态，且自身日志为空。

**根因**：docker-compose.yml 用 `depends_on: condition: service_healthy` 声明依赖。postgres、redis、kafka 未通过健康检查时，依赖它们的服务不会启动。kafka 是 content、upload、split、course、notification 的启动门禁（服务代码本身不在启动时连接 Kafka）。

```bash
# 先启动并等待基础设施健康
docker-compose up -d postgres redis zookeeper kafka
docker-compose exec -T postgres pg_isready -U app_user
docker-compose exec -T redis redis-cli ping
docker-compose exec -T kafka kafka-broker-api-versions --bootstrap-server localhost:9092

# 再启动应用服务
docker-compose up -d auth-service content-service
```

### 症状9：某一路由经网关持续 502，但容器内直连正常

服务容器状 态 `Up`，`curl http://localhost/api/split/tasks` 返回 502；同刻 `docker exec api_gateway wget -qO- http://split_service:8004/health` 却正常返回。

**根因**：nginx 在**配置加载时一次性**解析 `upstream { server split_service:8004; }` 并缓存容器 IP。容器重建/重启后拿到新 IP，网关仍往旧地址转发。网关日志里会看到旧 IP 与 `Connection refused`。

```bash
# 定界：拿到网关认为的上游地址
docker logs api_gateway 2>&1 | grep -i "upstream" | tail -3
#  connect() failed (111: Connection refused) ... upstream: "http://172.19.0.10:8004/..."

# 定界：容器内按服务名直连（这条通了就不是服务挂了）
docker exec api_gateway wget -qO- http://split_service:8004/health

# 恢复：让 nginx 重新解析上游
docker exec api_gateway nginx -s reload
```

> 登记为缺陷 BUG-016（部署配置类）。根治需给 `gateway/nginx.conf` 配 `resolver 127.0.0.11 valid=10s;` 并改用变量 `proxy_pass`，目前按运行手册规避。
> **测试含义**：E2E 首跑失败先走这一步定界——别把网关配置陈旧当成产品缺陷提单。

### 症状10：`curl http://localhost/api/auth/health` 返回 404

**根因**：网关只转发 `/api/*` 业务前缀，服务自身健康检查在**各自端口的 `/health`**（`services/*/app/main.py`）；网关代理的 `/health` 是网关自己的探活。因此健康检查只有两种正确打法：

```bash
curl http://localhost/health        # 网关自身 → 200 healthy
curl http://localhost:8001/health   # 服务自身（8001-8007 类推）→ 200 {"status":"healthy"}
curl http://localhost/api/feed/hot?page=1   # 经网关验业务链路可达（带鉴权接口返回 401/403 也算通）
```

> 旧版 README「验证」段曾写 `curl http://localhost/api/auth/health`，实为 404（缺陷 BUG-017，已修）。

## 三、系统化排查步骤

### 步骤1：检查基础设施

```bash
docker-compose ps
docker-compose exec -T postgres pg_isready -U app_user
docker-compose exec -T redis redis-cli ping
docker-compose exec -T kafka kafka-broker-api-versions --bootstrap-server localhost:9092
```

### 步骤2：检查服务日志

```bash
docker-compose logs --tail=100
docker-compose logs -f auth-service
docker-compose logs -f content-service
docker-compose logs | grep -i error
docker-compose logs | grep -i exception
docker-compose logs | grep -i traceback
```

### 步骤3：测试服务连接

```bash
curl http://localhost:8001/health
curl http://localhost:8002/health
curl http://localhost:8001/
curl http://localhost:8002/
curl -v http://localhost:8001/health
```

### 步骤4：容器内验证代码

```bash
docker-compose exec auth-service bash

# 在容器内（PYTHONPATH=/app）验证配置与导入
python -c "from common.config.settings import settings; print(settings.DATABASE_URL)"
python -c "from common.database.connection import get_db; print('OK')"
python -c "import sys; print('\n'.join(sys.path))"
python -c "from common.models import User; print('Common模块导入成功')"
```

## 四、获取详细错误信息

```bash
# 完整日志
docker-compose logs > all_logs.txt
docker-compose logs auth-service > auth_logs.txt

# 容器内调试
docker-compose exec auth-service bash
python -c "import sys; sys.path.append('/app'); from common.config.settings import settings; print(settings.DATABASE_URL)"

# 重建镜像并查看构建日志
docker-compose build --no-cache auth-service
docker-compose build auth-service 2>&1 | tee build.log
```

## 五、需要帮助时提供的信息

1. **服务状态**：`docker-compose ps` 的输出
2. **错误日志**：`docker-compose logs [service_name]` 的输出
3. **健康检查结果**：`curl http://localhost:8001/health` 的结果
4. **Docker版本**：`docker --version` 和 `docker-compose --version`
5. **系统信息**：操作系统版本

## 六、验证清单

启动成功后，应该能够：

- [ ] `docker-compose ps` 显示所有服务为 "Up"
- [ ] `curl http://localhost:8001/health` 返回包含 `"status":"healthy"` 的 JSON
- [ ] `curl http://localhost:8002/health` 返回包含 `"status":"healthy"` 的 JSON
- [ ] `curl http://localhost/health` 返回 `healthy`（网关）
- [ ] 可以访问 `http://localhost:8001/docs` 看到 API 文档
- [ ] 数据库连接正常（无连接错误日志）
- [ ] Redis 连接正常（无连接错误日志）
