# 测试设计文档

> 本平台（短视频学习平台）测试体系的设计思路与方法论说明。
> 面向测试/测开岗位面试的完整阐述，所有用例均可溯源到 `backend/tests/` 与 `frontend/src/__tests__/` 的代码。

---

## 1. 测试分层策略：为什么"接口密集"项目反过来以集成测试为主

经典测试金字塔建议单元测试占大头，但本项目是**接口密集型**系统——56 个 REST 接口的鉴权、参数校验、业务规则、数据库副作用才是核心风险，这些恰恰是单元测试覆盖不到的。因此采用与金字塔互补的分层：

```
        ┌──────────────┐
        │  E2E (6)     │  Playwright 真实浏览器链路冒烟（进 CI）
        ├──────────────┤
       │  API 集成     │  165 用例：真实 PostgreSQL，每个用例建表+删表完全隔离
      │  (17 文件)     │  覆盖：鉴权边界 / 业务规则 / 数据库副作用 / 幂等性 / 安全
     ├──────────────┤
    │  单元测试      │  151 用例：推荐算法 / 工具函数 / AI 降级 / 解析器 / 存储
   │  (15 文件)      │  不连库、不连网，纯逻辑快速回归
   └──────────────┘
   （315 例自动化之外，另有手动用例清单：发布前冒烟 13 条 + 探索 8 条 + 视觉 8 条，
    见《手动测试用例清单.md》——机器能稳定断言的归自动化，需要人眼/手感判断的留手动）
```

**为什么不 mock 数据库？** ORM 生成的 SQL、约束、索引、级联这些"跨层行为"只有真实数据库能验证。本套件实际抓到过：外键约束必现错误、唯一键冲突、点赞计数与行数不一致——内存 mock 根本发现不了（见 §5 缺陷驱动案例）。

**速度为什么能接受？** 用例粒度是接口级（毫秒/请求）、数据库会话池化复用、每个用例只建删表不重建库、TestClient 直连应用不走网络——315 用例全量回归约 13 秒（修复 celery 慢用例后从 29s 优化而来）。

## 2. 用例设计方法（等价类 / 边界值 / 场景法）

### 2.1 等价类划分法

以**登录（短信验证码）接口**为例（`tests/api/test_auth.py`）：

| 输入 | 有效等价类 | 无效等价类 | 用例断言 |
|------|-----------|-----------|---------|
| 手机号 | 11 位数字 | <11 位 / >11 位 / 含非数字 | 400/422，不发送验证码 |
| 验证码 | 6 位数字（与 Redis 存储一致） | 错误验证码 / 过期验证码 / 格式非法 | 401 或业务码，不签发 token |
| 凭证 | 有效 JWT | 无凭证 / 伪造 / 过期 / 篡改签名 | 403 / 401 / 401 / 401（认证边界矩阵） |

对应代码：`tests/api/test_auth.py::TestLogin`、`tests/api/test_security.py::TestAuthBoundary`。

### 2.2 边界值分析

| 接口 | 边界 | 边界内 | 边界外 | 用例文件 |
|------|------|--------|--------|---------|
| feed/search 分页 | page_size ∈ [1, 50] | 1、50 正常返回 | 0、51 → 422 | `test_feed.py` |
| 搜索关键词 | q ∈ [1, 100] 字符 | 1 字符、100 字符 | 空串、101 字符 → 422 | `test_search.py` |
| 上传分片 | 5MB/片 | 恰好 5MB 边界分片 | 超限 → 拒绝 | `test_upload*.py` |
| 手机号 | 恰好 11 位 | 11 位通过 | 10 位/12 位被拦截 | `test_auth.py`、前端 `Login.test.tsx` |
| 点赞计数 | 多用户聚合 | 1 用户 / 2 用户计数正确 | 重复点赞不重复计数 | `test_idempotency.py` |

### 2.3 场景法（业务链路）

上传链路主成功场景与异常场景（`tests/api/test_upload_merge.py`、`test_upload.py`）：

```
主场景: init(创建 UploadTask) → chunk(PUT 二进制分片, upload_id/chunk_index 走请求头)
        → complete(合并 → 大小校验 → MD5 → 落盘 → 创建 Video/LongVideo) → 200 + video_id
备选场景1: 分片缺失 → complete 报错且不产生脏数据（回滚）
备选场景2: 分片重复上传 → 覆盖而非追加（幂等）
备选场景3: 并发 complete → 唯一约束兜底，不重复创建视频
```

智能切分链路场景（`tests/api/test_split*.py`、`test_smart_split_service.py`）：

```
主场景: analyze(ffmpeg 提音频 → SenseVoice 转写 → GLM 知识点分析 → 切分建议)
降级场景1: GLM_API_KEY 未配置 → 自动降级为等长切分（不崩溃、可预期）
降级场景2: 重型 AI 依赖(torch/opencv)缺失 → 明确报错而非隐式失败
权限场景: 非作者访问他人切分任务 → 403
```

### 2.4 状态迁移法

点赞状态机（`tests/api/test_idempotency.py::TestLikeIdempotency`）：

```
         like         like         like
未点赞 ──────→ 已点赞 ──────→ 未点赞 ──────→ 已点赞
                 ↑ 每次切换断言：is_liked 与 like_count 一致，数据库行数始终 1
```

### 2.5 安全与异常路径（错误猜测法）

- **SQL 注入**：注入载荷 `' OR '1'='1` 被参数化查询视为字面量——不报 500、不泄露数据（`test_security.py::TestSQLInjection`）
- **LIKE 通配符**：`%`、`_` 未转义可匹配全部视频——修复后按字面量匹配（`test_security.py`，缺陷回归见 §5）
- **错误语义**：操作不存在的资源返回 404 而非 500；422 校验错误不落库

## 3. 测试数据管理

- **fixtures 分层**（`tests/conftest.py`）：
  - `db`：每个用例前 `create_all` 建全部表，用例后 DROP 全部表（CASCADE）→ 完全隔离；**清理失败显式 `pytest.fail`**（杜绝表残留 → 下个用例跑旧结构）
  - `client` + 各服务 client：TestClient 直连应用 + `dependency_overrides[get_db]` → 不经网络、走完整路由
  - `test_user / test_user2`：多角色数据，支撑权限与多用户聚合断言
  - `auth_headers`：有效凭证；无效/过期/伪造凭证由测试内构造（`_expired_token()`/`_forge_token()`）
  - `_lock_redis_memory_store`（autouse）：patch 三个 `get_redis` 入口（redis_client/stats/split 模块）返回 None，**测试行为与 Redis 是否可用无关**；每用例后清空验证码内存 store
- **唯一性保障**：所有 fixture 数据用 `uuid4` 生成，避免用例间 ID 碰撞；新用户手机号用 uuid 生成保证用例可重复执行
- **参数化数据**：矩阵参数表静态可收集（动态 fixture 值用构造器 lambda 惰性解析），`id=` 命名保证失败定位

## 4. 前端测试（Vitest + React Testing Library）

前端 10 用例（`frontend/src/__tests__/`），黑盒行为验证：

| 文件 | 覆盖点 |
|------|--------|
| `Login.test.tsx` (4) | 非法手机号拦截 / 验证码输入框时序出现 / 错误验证码 / 登录成功跳转 |
| `AuthContext.test.tsx` (3) | login 持久化 token / logout 清理 / updateUser 状态迁移 |
| `ProtectedRoute.test.tsx` (3) | 未登录重定向 / 已登录放行 / Loading 态不闪跳 |

设计原则：mock 最小化（只 mock `useAuth` 副作用），路由与渲染走真实实现；断言用户可见行为而非内部实现。

## 5. 缺陷驱动用例（Bug 复现 → 修复 → 回归闭环）

| 缺陷 | 发现方式 | 用例形态 | 修复 | 回归 |
|------|---------|---------|------|------|
| 上传 complete 接口"静默成功"（控制流分支缩进错误，返回 200+null） | 集成测试断言 data 结构 | 断言成功响应必须含 video 数据 | 修正分支逻辑 | 用例转绿即回归 |
| confirm 接口外键约束必现错误 | 真实 PostgreSQL 约束校验 | 关联不存在的外键 → 预期 400 而非 500 | 加业务校验 | 同上 |
| 搜索未转义 LIKE 通配符，`q=%` 匹配全部视频 | 安全专项测试 | `xfail(strict)` 复现用例 | `ilike(..., escape='\\')` 转义 `% _ \` | 移除 xfail 转正常用例 |
| 热度推荐 `ORDER BY created_at DESC, popularity_score DESC`，高热旧视频排不过冷新视频 | 单测断言排序语义 | `xfail(strict)` 复现用例 | 热度分主导、时间仅作同分次要键 | 移除 xfail 转正常用例 |
| learn complete 字段名错配（测试提交 `completed_ratio`，接口字段是 `completion_rate`，Pydantic 忽略未知字段 → 断言从未生效、complete 分支零覆盖） | 二轮 review 对照源码核验 | 改用正确字段名 + DB 落库断言（status/completed_ratio） | 测试修正（接口契约本无 bug，是测试没测到点上） | DB 断言兜底 |
| search `sort_by=hot` 伪实现（与 latest 同序，注释自认） | 二轮 review 发现 + 排序语义用例 | 建两个互动量不同的视频断言 hot 排序在前 | 互动总量聚合排序（outerjoin Like/Favorite/Comment） | 排序断言 |
| 无效 base64 图片上传返回 500（客户端输入错误当服务器错误） | 二轮 review 发现（测试把 500 当契约固化） | 断言 422 + code 422 | `binascii.Error`/`ValueError` 单独捕获返回 422 | 测试转绿即回归 |

**实践要点**：先写"缺陷复现用例"（必须失败），修复后用例转绿即完成闭环——这比"修完再补测试"更能证明测试的有效性。两个 xfail 用例原本标记"已知缺陷"，现已修复并转为普通回归用例（2026-08）；二轮 review 又驱动修复 3 个服务端缺陷（含 2 个"测试形同虚设"类问题）。

## 6. 持续集成与质量门禁

```
GitHub Actions (test.yml)
├── test job      后端 315 用例 + 覆盖率门禁 --cov-fail-under=70（实测 75.5%）
│                 + 分级门禁 scripts/check_coverage_gates.py（5 个核心业务模块独立底线）
├── frontend job  前端 Vitest 10 用例
└── e2e job       Playwright 6 冒烟用例（4 微服务 + nginx 网关 + 前端 dev server，
                  镜像本地开发链路，失败上传 trace/screenshot 现场）
```

质量门禁四件套：**全量回归必须绿 → 总量覆盖率低于 70% 直接失败 → 核心业务模块分级门禁（防被总量掩盖）→ E2E 冒烟守核心链路**。

分级门禁模块底线（当前实测值向下取整防回退）：

| 模块 | 底线 |
|---|---|
| smart_split/keyframe_extractor.py | 10% |
| smart_split/video_splitter.py | 15% |
| smart_split_service.py | 45% |
| smart_split/knowledge_analyzer.py | 60% |
| smart_split/speech_to_text.py | 60% |

> 智能切分管线是"智能"卖点，但覆盖率远低于总量（keyframe_extractor 11% / video_splitter 15%），被高覆盖模型文件抬平——分级门禁让失守模块显形。

## 7. 手动测试：自动化判不了的部分

自动化用例（315 例）负责**回归**，但有三类场景机器判不了：**视觉体验**（布局/动效/空状态好不好看）、**探索性发现**（自动化想不到的缺陷）、**上线人工确认**（人用起来顺不顺）。因此维护一份手动用例清单（《手动测试用例清单.md》）：

| 清单 | 数量 | 执行时机 |
|---|---|---|
| 发布前人工冒烟（S1–S13） | 13 条 | 每次上线前，约 5 分钟 |
| 探索性测试（E1–E8） | 8 条 | 新功能首测 / 定期抽查 |
| 视觉验收（V1–V8） | 8 条 | 前端改版后 |

**分工原则**：机器能稳定断言的归自动化（进 CI 每次跑），需要人眼/手感判断的留手动（按需跑）。
探索性测试发现的缺陷，筛选后沉淀为自动化回归用例（复现闭环，见 §5）——手动测试是自动化的**发现源头**，不是被淘汰的旧做法。

## 8. 方法论小结（面试可复述）

1. **测试的价值不在"写断言"，而在"发现缺陷"**——本套件真实抓到 7 类缺陷（含 2 个 xfail 回归闭环、3 个 review 驱动修复），且全部以用例形式沉淀为回归资产
2. **分层不是教条**——接口密集项目把集成测试做厚、单元测试留给纯逻辑，回归速度（13s，修复 celery 慢用例后）与发现能力（真库约束）双赢
3. **数据库副作用是接口测试的第一断言对象**——状态码 + 响应体 + 数据库最终态三者缺一不可（learn/inbox/follow/course 已全部补齐）
4. **缺陷管理闭环**——复现用例（xfail strict）→ 修复 → 移除标记转绿，缺陷从"口头描述"变成"可回归的资产"
5. **外部依赖要可预期**——AI 依赖缺失要有明确降级路径（GLM 降级等长切分）；Redis 测试锁定内存路径、celery 测试 patch 掉，测试行为与环境无关
6. **数据驱动不是合并函数，是吃透被测逻辑**——43 例参数化矩阵覆盖认证/输入/工厂分支；动态 fixture 值用构造器惰性解析，参数表静态可收集
7. **覆盖率高不代表测得好**——75.5% 总量掩盖了智能切分管线 11% 的裸露，分级门禁让失守模块显形
