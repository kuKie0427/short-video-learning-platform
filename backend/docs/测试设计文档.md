# 测试设计文档

> 本平台（短视频学习平台）测试体系的策略与用例体系说明。
> 本文回答"测什么、为什么这么测、用例怎么设计"；环境与命令见《运行测试.md》，人工验收条目见《手动测试用例清单.md》，套件就近速查见 [tests/README.md](../tests/README.md)。
> 所有用例均可溯源到 `backend/tests/`、`frontend/src/__tests__/`、`e2e/tests/` 的代码。

## 1. 体系总览与分层策略

自动化用例共 **331 条**：后端 pytest **315 条**（API 集成 164 + 单元 151，合计 32 个测试文件）、前端 Vitest **10 条**、Playwright E2E **6 条**。手工侧两套口径：**正式版 56 条编号用例**（冒烟 16 + 核心 28 + 探索 8 + 兼容 4，另沿用视觉 V1-V8），以及由其压缩出的**快查清单 29 条**（冒烟 13 + 探索 8 + 视觉 8）——前者是执行与留痕的主台账，后者是上线前 5 分钟过一遗用的快查版，两者不是两套用例。

```
        ┌──────────────┐
        │  E2E (6)     │  Playwright 真实浏览器链路冒烟（进 CI）
        ├──────────────┤
       │  API 集成     │  164 条（17 文件）：真实 PostgreSQL，逐用例建表+删表完全隔离
      │  (17 文件)     │  覆盖：鉴权边界 / 业务规则 / 数据库副作用 / 幂等性 / 安全
     ├──────────────┤
    │  单元测试      │  151 条（15 文件）：推荐算法 / 工具函数 / AI 降级 / 解析器 / 存储
   └──────────────┘
```

本项目是**接口密集型**系统：56 个 REST 接口的鉴权、参数校验、业务规则、数据库副作用才是核心风险，这些恰恰是单元测试覆盖不到的。因此采用与经典金字塔互补的分层：**把集成测试做厚、单元测试留给纯逻辑**。

**为什么不 mock 数据库？** ORM 生成的 SQL、约束、索引、级联这些"跨层行为"只有真实数据库能验证。外键约束冲突、唯一键冲突、点赞计数与行数不一致这类问题，内存 mock 发现不了。因此集成层连真实 PostgreSQL（`tests/conftest.py` 以 `postgresql+psycopg://` 构造测试库连接）。

**速度为什么能接受？** 用例粒度是接口级（毫秒/请求）；数据库引擎模块级单例、会话池化复用（pool_size=2）；每个用例只建删表不重建库；TestClient 直连 ASGI 应用不走网络。全量 315 例跑完耗时在 20 秒量级（2026-09-09 复测：纯用例 17.7–19.5s、含覆盖率报告 22s；轻负载历史实测 12.7–13s），无需并行即可进 CI。

## 2. 用例设计方法（等价类 / 边界值 / 场景法 / 状态迁移 / 错误猜测）

### 2.1 等价类划分法

以**登录（短信验证码）接口**为例（`tests/api/test_auth.py`）：

| 输入 | 有效等价类 | 无效等价类 | 用例断言 |
| ------ | ----------- | ----------- | --------- |
| 手机号 | 长度 ≥ 10 的非空字符串 | 缺失 / 长度 < 10 | 422，不发送验证码 |
| 验证码 | 6 位数字（与 Redis/内存存储一致） | 错误验证码 / 过期验证码 | 400 + 业务错误信息，不签发 token |
| 凭证 | 有效 JWT | 无凭证 / 伪造签名 / 过期 / 缺失 sub | 403 / 401 / 401 / 401（认证边界矩阵） |

对应代码：`tests/api/test_auth.py`（`test_send_code_phone_matrix`、`test_login_matrix`、`test_get_profile_token_matrix`、`test_refresh_token_matrix`）、`tests/api/test_security.py::TestAuthBoundary`（`test_write_with_invalid_credentials` 四参数矩阵）。

### 2.2 边界值分析

| 接口 | 边界 | 边界内 | 边界外 | 用例文件 |
| ------ | ------ | -------- | -------- | --------- |
| 分页边界 | `page_size ∈ [1, 50]`（`Query(20, ge=1, le=50)`，`/api/feed/search`、`/api/search/videos` 等一致） | 1、50 正常返回 | 0、51 → 422 | `test_feed.py`、`test_security.py` |
| 关键词长度（**按端点分别验**） | `/api/feed/search`（feed.py:737）与 `/api/search/suggest`（search.py:20）声明 `q ∈ [1,100]` | 1 字符、100 字符 | 空串、101 字符 → 422 | `test_search.py`、`test_security.py`；手工用例 R05 |
| └ 已知不一致（未修） | `/api/search/videos`（search.py:78）的 `q` 为 `Optional[str]` 且无长度约束 | — | 实测空串与 101 字符均返回 200 | 记入《测试总结报告》遗留风险 5；同源规则不一致与 BUG-006 同类，修它需统一三端点契约并补参数化用例 |
| 上传分片 | 5MB/片（init 响应声明 `chunk_size: 5242880`，客户端契约） | 按声明大小分片 | 分片缺失 / 重复 / 非法索引被拦截 | `test_upload.py`、`test_upload_merge.py`、`test_idempotency.py` |
| 手机号 | 后端 `/auth/send-code` 校长度 ≥ 10；前端登录页卡 `length === 11` 单点分支 | 后端：10/11 位进有效类；前端：11 位 | 后端：9 位 → 422；前端：9/10/12 位均被拦（不发码、不出验证码框） | `test_auth.py::test_send_code_phone_matrix`、前端 `Login.test.tsx`、手工 A01-A03 |
| 点赞计数 | 多用户聚合 | 1 用户 / 2 用户计数正确 | 重复点赞不重复计数 | `test_idempotency.py` |

### 2.3 场景法（业务链路）

上传链路主成功场景与异常场景（`tests/api/test_upload_merge.py`、`test_upload.py`）：

```
主场景: init(创建 UploadTask) → chunk(PUT 二进制分片, upload_id/chunk_index 走请求头)
        → complete(合并 → 大小校验 → MD5 → 落盘 → 创建 Video/LongVideo) → 200 + video_id
备选场景1: 分片缺失 → complete 报错且不产生脏数据（回滚）
备选场景2: 分片重复上传 → 覆盖而非追加（幂等）
备选场景3: 并发 complete → 唯一约束兜底，不重复创建视频
```

智能切分链路场景（`tests/api/test_split*.py`、`tests/unit/test_smart_split_service.py`）：

```
主场景: analyze(ffmpeg 提音频 → SenseVoice 转写 → GLM 知识点分析 → 切分建议)
降级场景1: GLM_API_KEY 未配置 → 自动降级为等长切分（不崩溃、可预期）
降级场景2: 重型 AI 依赖(torch/opencv)缺失 → 明确报错而非隐式失败
权限场景: 非作者访问他人切分任务 → 403
```

### 2.4 状态迁移法

点赞状态机（`tests/api/test_idempotency.py::TestLikeIdempotency`）：

```
         like         unlike        like
未点赞 ──────→ 已点赞 ──────→ 未点赞 ──────→ 已点赞
                 ↑ 每次切换断言：is_liked 与 like_count 一致，数据库行数始终 1
```

### 2.5 安全与异常路径（错误猜测法）

- **SQL 注入**：注入载荷 `' OR '1'='1` 被参数化查询视为字面量，不报 500、不泄露数据（`test_security.py::TestSQLInjection`）
- **LIKE 通配符**：搜索词中的 `%`、`_`、`\` 被转义后按字面量匹配（`ilike(..., escape='\\')`），`q=%` 不匹配全部视频（`test_security.py`）
- **错误语义**：操作不存在的资源返回 404 而非 500；422 校验错误不落库
- **输入错误与服务器错误分界**：无效 base64 图片数据由 `binascii.Error`/`ValueError` 捕获返回 422，不冒泡成 500（`test_security.py`）

## 3. 测试数据管理

全部集中在 `tests/conftest.py`（仓库唯一 conftest，无嵌套）：

- **数据库夹具 `db`**（function 作用域）：用例前 `create_all` 建全部表，用例后逐表 `DROP ... CASCADE` 完全隔离；清理失败走 `drop_all` 兜底，再失败显式 `pytest.fail`。表残留会让下个用例在旧表结构上静默运行，宁可报错不可吞
- **ASGI 直连客户端**：`create_test_client(app, db)` 用 `dependency_overrides[get_db]` 把应用切到测试会话，`TestClient` 直接调用 ASGI 应用，不经网络、走完整路由与中间件。按服务提供 `client`（Content）、`auth_client`、`upload_client`、`split_client`、`course_client`、`search_client`、`notification_client` 七个夹具
- **角色与凭证**：`test_user / test_user2` 支撑权限与多用户聚合断言；`auth_headers / auth_headers_user2` 签发有效 JWT；无效/过期/伪造凭证由测试内构造（`test_security.py` 的 `_expired_token()`/`_forge_token()`）
- **Redis 锁定**（autouse `_lock_redis_memory_store`）：patch 三个 `get_redis` 入口（redis_client/stats/split 模块）返回 None，短信验证码等走内存降级路径，**测试行为与 Redis 是否可用无关**；每用例后清空内存 store，杜绝验证码 key 跨用例残留
- **外部任务队列**：split 测试 monkeypatch `celery_app.send_task`，不真发消息（测试环境无 broker，真实调用会同步重试拖慢用例）
- **唯一性保障**：fixture 数据用 faker `uuid4`/`unique.phone_number()` 生成，用例可重复执行
- **参数化矩阵**：42 条用例来自 13 个 `@pytest.mark.parametrize`（认证边界矩阵、输入校验矩阵、登录验证码矩阵、存储工厂分支矩阵等）；动态 fixture 值用构造器 lambda 惰性解析，参数表静态可收集；`id=` 命名保证失败定位可读

断言标准：**状态码 + 响应体 + 数据库最终态**三者缺一不可。接口返回 200 不代表业务落库正确（learn/inbox/follow/course 均按此实现）。

## 4. 关键行为锁定（专项用例）

以下行为各有专门用例锁定。它们的共同点：接口表面"成功"不代表正确，必须断言到契约字段与数据库最终态。这类问题曾以真实缺陷形态出现，用例是它们的永久回归防线。

| 被锁定的系统行为 | 断言要点 | 用例位置 |
| ------ | --------- | --------- |
| 上传 complete 成功响应必须含业务数据 | 拒绝"200 + data=null"的静默成功，断言 video_id/status/file_url 与落库记录 | `test_upload_merge.py` |
| 外键引用不存在 → 400 业务错误 | 不让约束异常裸奔成 500 | `test_course.py`、`test_security.py` |
| 搜索 `%`/`_`/`\` 按字面量匹配 | `q=%` 不返回全部视频 | `test_security.py`（转义实现：`feed.py`、`search.py` 的 `ilike(..., escape='\\')`） |
| 热度排序：popularity_score 主导，created_at 仅作同分次要键 | 高热旧视频排在冷新视频之前 | `test_recommendation.py` |
| search `sort_by=hot` 与 `latest` 产生不同序 | 建互动量不同的两视频，断言 hot 序在前 | `test_search.py`（实现：outerjoin Like/Favorite/Comment 聚合计数） |
| learn complete 请求字段 `completion_rate` 落库到 `completed_ratio` | 提交后断言 DB 记录的完成率与状态（契约字段见 `services/content/app/api/learn.py`） | `test_learn.py` |
| 无效 base64 图片 → 422 + code 422 | 客户端输入错误不当服务器错误 | `test_security.py`（实现：`upload.py` 捕获 `binascii.Error`） |
| 点赞/关注/分片重传的幂等性 | 重复请求计数不漂移、分片覆盖不追加、唯一约束兜底 | `test_idempotency.py` |

**缺陷入库机制**：发现缺陷先写复现用例（必须失败，必要时 `xfail(strict)` 强制回归），修复后移除标记转普通用例。缺陷从"口头描述"变成"可回归的资产"。套件中无 xfail 用例；3 处 `pytest.skip` 均为环境守卫（AI 依赖已安装时跳过缺失路径用例、仅开发环境生效的 UUID 直通/自动建用户开关）。

## 6. E2E 冒烟（Playwright）

6 条用例（5 个 spec 文件，详见 `e2e/README.md`）：登录流程、登录校验、首页推荐流渲染、搜索、真实文件分片上传、direct-split 切分全链路。

## 7. 持续集成与质量门禁

`.github/workflows/test.yml` 三个 job：

```
├── test       后端 315 用例全量回归（PostgreSQL 服务容器 + ffmpeg）
│              + 总量门禁 --cov-fail-under=70（pytest.ini 内置，全量实测 75.4%）
│              + 分级门禁 scripts/check_coverage_gates.py（5 个核心模块独立底线）
├── frontend   Vitest 10 用例 + ESLint 0 error + 生产构建（tsc + vite）
└── e2e        Playwright 6 冒烟（依赖 test/frontend 通过；postgres+redis 容器、
               5 微服务 + nginx-ci + 前端 dev server；失败上传测试现场）
```

质量门禁四件套：**全量回归必须绿 → 总量覆盖率低于 70% 直接失败 → 核心业务模块分级门禁（防被总量掩盖）→ E2E 冒烟守核心链路**。

分级门禁（`scripts/check_coverage_gates.py`，底线为实测值向下取整防回退）：

| 模块（backend 相对路径） | 底线 |
| --- | --- |
| services/split/app/services/smart_split/keyframe_extractor.py | 10% |
| services/split/app/services/video_splitter.py | 15% |
| services/split/app/services/smart_split_service.py | 45% |
| services/split/app/services/smart_split/knowledge_analyzer.py | 60% |
| services/split/app/services/smart_split/speech_to_text.py | 60% |

智能切分管线是产品"智能"卖点所在，但覆盖率显著低于总量，容易被高覆盖的模型文件抬平。分级门禁让失守模块显形，总量数字掩盖不了单点裸奔。

## 8. 手动测试：自动化判不了的部分

自动化负责**回归**（证明改动没破坏已有行为），三类场景机器判不了，留给人工（条目见《手动测试用例清单.md》）：

| 清单 | 数量 | 执行时机 |
| --- | --- | --- |
| 发布前人工冒烟（正式版 S01-S16；快查清单 S1-S13） | 16 条 | 每次上线前，约 5 分钟 |
| 探索性测试（E1-E8） | 8 条 | 新功能首测 / 定期抽查 |
| 视觉验收（V1-V8） | 8 条 | 前端改版后 |

**分工原则**：机器能稳定断言的归自动化（进 CI 每次跑），需要人眼/手感判断的留手动（按需跑）。典型分界：`feed/recommend` 返回 200 且字段完整 → 自动化；推荐流"看起来是否真的个性化" → 手动。

**执行留痕**：手工结果写回[手工测试用例-正式版](手工测试用例-正式版.md)的"实际/状态"列，截图存 [`manual-evidence/`](manual-evidence/)（命名 `用例编号-序号.png`）；UI 类可用 `cd e2e && npm run evidence` 逐例抓截图与 trace 后归档。未执行项保留 ☐ 并逐条写明阻塞原因——**记"没跑"比空着或打钩更可信**。

探索性测试发现的缺陷，筛选后按 §4 的复现机制沉淀为自动化回归用例。手动测试是自动化的发现源头，不是被淘汰的旧做法。

> 执行自己写的用例也能发现自己的错：2026-09-09 复跑即发现 I01（把 toggle 接口的预期写成"恰 1 行"）、U08（越权应预期 404 而非 403）、R05（未区分搜索类三端点的长度规则）三处用例口径错误，已按实测行为勘误（见正式版 §七）。

## 9. 方法论小结

1. **测试的价值在发现缺陷，不在写断言**。§4 每条专项用例都对应一类"表面成功、实际错误"的真实缺陷，并以回归资产形态长期驻留套件
2. **分层不是教条**。接口密集项目把集成测试做厚（164 条连真库）、单元测试留给纯逻辑（151 条），回归速度（315 例 20 秒量级）与发现能力（真库约束）双赢
3. **数据库副作用是接口测试的第一断言对象**。状态码 + 响应体 + 数据库最终态三者缺一不可
4. **缺陷管理闭环**。复现用例（xfail strict）→ 修复 → 移除标记转绿，缺陷变成可回归的资产
5. **外部依赖要可预期**。Redis 锁定内存路径、celery patch 掉、AI 依赖缺失走显式降级：测试行为与环境无关
6. **数据驱动不是合并函数，是吃透被测逻辑**。42 例参数化矩阵覆盖认证/输入/工厂分支；动态值惰性解析，参数表静态可收集
7. **覆盖率高不代表测得好**。75.4% 的总量掩盖不了智能切分管线的低覆盖，分级门禁让失守模块显形
