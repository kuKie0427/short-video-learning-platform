### 200 并发瓶颈定位（per-endpoint，results CSV）

| 接口 | 请求数 | P50 | P95 | Max | 失败 |

### 容量结论（实测，非推测）

1. **吞吐天花板 ≈ 73 RPS**：100→200 用户负载翻倍，RPS 仅从 68→73——服务端饱和，增量压力转化为排队时延（P95 520ms→2.7s）。
2. **P95<500ms 门禁本机天花板 ≈ 90-100 用户**：90 并发过线（410ms），100 并发临界超标（520ms）。
3. **瓶颈完全定位到 content 服务**：recommend（4 算法混合）与 hot（时间衰减排序）P95 同为 2.8s 量级；同机 auth/search 高压下仍 <20ms——不是环境整体过载，是单链路 CPU 密集+单进程部署。
4. **全阶梯 0 失败**：饱和表现为延迟升高的优雅降级（闭环压力模型：思考时间+响应时间自动压低需求率），无超时/崩溃/连接拒绝——容量描述完整。
5. **利特尔法则核验**：200 用户闭环需求率 ≈ 200/1.25s(平均思考) = 160 RPS > 天花板 73 → 排队；实测在途并发 = 73 RPS × ~1.3s 平均响应 ≈ 95，与"90 过线/100 超标"拐点互证。

### 瓶颈定位实验（2026-09-04，回答"73 RPS 天花板从哪来"）

**代码证据**：
- `/recommend`、`/hot` handler 均为 `async def`，但函数体内全部是**同步** SQLAlchemy（Session.query）+ 纯 Python 4 算法混合计算/排序——同步代码写在 async handler 里 = **直接阻塞事件循环**（不走线程池），content 进程内所有请求严格串行。
- Redis 缓存层代码存在（`RecommendationService` 按 user×strategy 缓存 1h），但基线环境 **Redis 未启用**，`get_redis()` 返回 None 时降级为每请求全量重算——命中路径只是一条 `IN` 查询，成本差两个量级。

**实验①（200 并发稳态 10s 窗口 CPU 差值）**：content 进程耗 **7.83s**（≈78% 单核：CPU 计算 + 同步 DB 等待全部串行在循环里）；auth 0.11s、locust 客户端 0.47s——**排除整机过载与发压机瓶颈**。

**实验③（content 起 `--workers 4`，200 并发 60s 复跑）**：

| 配置 | RPS | 聚合 P95 | 失败率 | 门禁 |
|---|---|---|---|---|
| 单进程（原） | 73.2 | 2700ms | 0% | ❌ |
| **content×4 worker** | **156.2** | **150ms** | **0%** | ✅ |

吞吐 ×2.1（逼近发压机闭环需求率上限 ~160）、P95 ÷18——**瓶颈=单进程（GIL+事件循环）串行化，非机器/非数据库/非网络**；数据文件同目录前缀 `locust_20260904_u200*`，workers 轮控制台记录于本报告。

**修复优先级（容量结论）**：① 推荐流启用 Redis 缓存（业务正确：推荐不该每请求重算，单进程即可回到毫秒级）② 多 worker 部署（compose/Dockerfile 生产形态本就应多进程）③ 若需再压榨：把 4 算法计算移出请求路径（预计算/异步任务）。

**实验②（Redis 启用对照，2026-09-04——本机无 redis 二进制，用镜像源拉 `redis:7-alpine` 容器 6379，唯一变量=缓存开）**：

| 200 并发 @ 单进程 | 无 Redis（基线） | 有 Redis | 变化 |
|---|---|---|---|
| 聚合 RPS | 73.2 | **157.4** | ×2.1（顶到发压机闭环需求率） |
| 聚合 P95 | 2700ms | **32ms** | ÷84，全过门禁 ✅ |
| recommend P95 | 2800ms | 43ms | ÷65（缓存命中路径=一条 IN 查询） |
| hot P95 | 2800ms | **41ms** | ÷68——**hot 自身无缓存代码**，纯粹是事件循环队头解除：此前每请求被 recommend 的 24ms 级同步重算霸占循环，连带排队 |
| 失败率 | 0% | 0% | — |

缓存对账（诚实性核验）：`keyspace_hits 3417 / misses 1273`，misses 非缓存抖动——受控实验（20×profile+20×search → misses 恰 +20）证实 **auth profile 每请求固有 1 次 Redis 键探测**（dev UUID 无会话键恒 miss，n≈1111）+ 首轮冷算与竞态零头；recommend（n=3360）命中率 ≈100%，预热 2 连击 66ms→8.4ms 可复核。

**结论（实验 ①②③ 三向定界后）**：73 RPS 天花板 = 单进程事件循环被 recommend 同步重算串行化。**首选修复=启用内置 Redis 缓存**（业务正确+性能正确双成立：单进程 32ms 反超 4 进程无缓存的 150ms）；多 worker 是并行次级手段；根治项为把 4 算法计算移出请求路径。

## 容器化整链路基线（2026-09-05，Docker 全栈 + 网关）

> 部署形态基线，脚本 `locustfile_gateway.py`（单 host 相对路径，打 Nginx 网关 :80）。
> 与上方本机直连微基准**互补且不可直接对比**：微基准回答"哪里慢"（受控变量归因），
> 本基线回答"生产部署形态整体表现"。每次部署形态相关改动（compose/网关/镜像）后重跑。

### 测试环境

| 项 | 值 |
|---|---|
| 测试日期 | 2026-09-05 |
| 机器 | macOS (Apple Silicon arm64)，Docker Desktop 29.0.1（VM 6 CPU / 8GB，宿主 24GB） |
| 被测链路 | Locust → Nginx 网关 :80 → 7 服务容器（auth/content/search 在链路内） |
| 数据库 | PostgreSQL 14 容器（`short_video_postgres`，mock 数据 **2 条视频**，`insert_mock_videos.py` 幂等灌入；⚠️ 本机基线为 8 条，脚本仅能复刻 2 条，数据量差异已如实标注） |
| Redis | **启用**（redis:7 容器；缓存命中已实证：recommend 双连击 55ms→10ms，`recommend:user:…:hybrid` 键可见） |
| 鉴权 | dev UUID token 直通（compose `ENVIRONMENT=development`），首次请求自动建 dev 用户 |
| 压测参数 | 三轮：sanity 20u/30s → 基线 20u/30s → 高压 200u/60s |

### 实测结果（原始数据：`results/locust_gateway_20260905_{sanity20,u20,u200}_*.csv`）

| 轮次 | 请求数 | 聚合 P95 | RPS | 失败率 | 门禁（200ms/1%） |
|---|---:|---:|---:|---:|---|
| sanity 20u | 455 | 21ms | 15.8 | 0.00% | ✅ |
| **基线 20u** | **458** | **19ms** | **15.8** | **0.00%** | ✅ **入库** |
| 高压 200u | 8717 | 47ms | 147.5（末窗 163） | 0.00% | ✅ |

200u 分接口 P95：recommend 60ms / hot 61ms / search 24-45ms / auth 10ms——全部走缓存命中路径，长尾收敛（max 254ms）。

### 与本机基线对照（回答"网关+容器化开销多大"）

| 200 并发对照 | 本机直连·无 Redis（9/4） | 本机直连·单进程+Redis（9/4） | **网关整链路+Redis（9/5，本节）** |
|---|---|---|---|
| 聚合 P95 | 2700ms（饱和） | 32ms | **47ms** |
| RPS | 73.2（天花板） | 157.4 | **147.5**（末窗 163） |
| 失败率 | 0% | 0% | 0% |

**结论**：① 部署形态完整保住"启用 Redis 缓存"修复收益——200 并发 P95 47ms / 0 失败，全过门禁，
较无缓存本机形态 P95 ÷57、吞吐 ×2；② 网关转发 + 容器化 + Docker PG 的叠加开销 ≈ **+15ms P95**
（47 vs 32）且吞吐同量级——相对于接口预算可忽略；③ 9/4"首选修复=Redis 缓存"的结论在
生产形态下成立（缓存命中路径单进程即够用）；④ 注意数据量差异（2 vs 8 条视频）对绝对值对比的影响，
二者数量级结论不受影响。
